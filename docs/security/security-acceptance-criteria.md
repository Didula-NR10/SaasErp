# Security acceptance criteria

Phase 04 — Task 01. These are planned verification scenarios, not executed results. Canonical requirements and their individual measurable criteria are in [security-requirements.md](security-requirements.md) and [security-principles.md](security-principles.md). Requirement IDs below are references; AC IDs identify tests rather than additional security requirements. This acceptance catalogue is complemented by the Stage A [SRTM](security-requirements-traceability-matrix.md), [threat model](threat-model.md), [boundary analysis](attack-surface-and-trust-boundaries.md) and proposed [ADR-0004](../adr/0004-authentication-and-session-architecture.md).

## Execution and evidence rules

Execute each applicable record’s positive and negative criteria at its named phase using its stated verification method. For every scenario below retain build/source revision, environment and role/tenant fixtures, selected policy values, redacted request/response evidence, persistent state assertions, result, timestamp and reviewer. A forbidden attempt passes only when it grants no extra authority, returns no forbidden data, creates no forbidden business side effect and produces the required redacted audit outcome. Exact error response design remains later work: unauthenticated API calls normally use 401, unauthorized authenticated calls use 403 or a consistently chosen non-enumerating 404, and infrastructure failures use a controlled error without granting access.

Use at least ordinary A-only, ordinary B-only, A-and-B member, revoked member, tenant administrator and platform privileged identities. Use distinct A/B database markers and identical logical Redis keys. Create synthetic credentials and payment/file fixtures; never use production secrets or print environment variables. Timing, quotas and deadlines must be configured and recorded, including the instant on either side of expiry. Verify denial in both responses and persisted state; UI appearance alone is insufficient.

Browser-token-specific scenarios are retired by approved ADR-0004. Native sessions remain subject to session and accepted cookie-replay tests. Deferred features require verification before exposure; source status is not an executed result. P0 failures block applicable feature/release acceptance; changes must not weaken existing isolation tests to pass.

## Task 01 documentation verification and manual review

Documentation checks cover unique canonical IDs, references resolving to defined requirements, required fields in every record, nonempty positive/negative criteria, category/status counts, relative file links, Markdown formatting and changes limited to the three requested documents. Git whitespace checks include newly created documents. No Java, frontend, SQL, Docker or workflow changes, commits, pushes, merges, builds or infrastructure operations are part of this task.

Manual review owners should:

1. Security architect: review scope, untrusted-client residual risk, assurance/recovery policy and open ADR questions; approve provisional numbers only with evidence.
2. Backend/data maintainers: confirm Phase 03 source descriptions and tenant persistence activation limits, raw JDBC ownership rules and shared-credential reach.
3. Frontend owner: validate CSP/Trusted Types and cross-origin compatibility and acknowledge same-origin malicious-code limitations.

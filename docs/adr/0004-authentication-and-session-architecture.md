# ADR-0004: Native company-bound server-side authentication sessions

Status: Accepted architecture by project-owner instruction, 2026-11-27. The owner reports the pre-Stage-03 foundation passed all 280 tests. Stage 03 MFA/account-protection changes are unverified and are not production-ready.

This decision supersedes the previous proposed browser JWT/DPoP authorization-window architecture and its qualification gates. It preserves ADR-0001–0003, Java 21, Spring Boot 4.2.0, React/Vite, one PostgreSQL database, platform/billing separation, schema-per-company routing, restricted runtime/migrator identities, existing tests and CI protections.

## Decision and accepted trade-off

Use native Spring Security password providers, AuthenticationManager, SecurityContext, CSRF and session-fixation protection. Use Spring Session Redis for HttpSession persistence. PostgreSQL writer records remain authoritative for accounts, memberships, company status/entitlements, security versions and session revocation. There is no authorization server, browser access JWT, browser DPoP, refresh-token family or popup communication. Obsolete SEC-TOKEN identifiers are retained as retired records; future external integrations require a separate decision.

A stolen valid session cookie may be replayable, including from another device. HttpOnly prevents ordinary JavaScript cookie reads; it does not prevent cookie theft through every channel or malicious same-origin requests. TLS, host isolation, session rotation, bounded lifetimes, current revocation checks and future transaction-bound step-up reduce but do not eliminate replay risk. This architecture does not provide equivalent browser-level proof-of-possession protection. Origin and CSRF checks do not stop an attacker who has stolen the session cookie and can obtain that session's CSRF token.

## Company origins, cookies and WebAuthn

Each company continues to operate React and same-origin `/api/v1` at its own approved HTTPS hostname, for example `https://abc.hich.com`. An operator-maintained exact origin allowlist and a unique PostgreSQL hostname-to-company mapping must agree for login. The request's company UUID, subdomain text or frontend roles alone never establish membership. A user authenticates separately on each company hostname. No parent-domain cookies, cross-origin credential exchange or silent cross-company SSO is introduced.

Production cookies are `__Host-HICHSESSION`, Secure, HttpOnly, Path=/, SameSite=Strict and have no Domain attribute. Remember-me and URL session tracking are unavailable. No authentication credentials enter localStorage, sessionStorage, IndexedDB, service-worker caches or URLs. There is no HTTP development exception in this batch; use local TLS. Existing prototype frontend state remains presentation data, not backend authority.

**WebAuthn RP decision:** use the exact company hostname as its RP ID and the exact corresponding HTTPS origin as the only ceremony origin. For ABC, RP ID `abc.hich.com`, origin `https://abc.hich.com`; for Royal, RP ID `royal.hich.com`, origin `https://royal.hich.com`. Never use `hich.com`, wildcard origins, related-origin delegation, a request-derived RP ID or a shared central RP for company ceremonies. Reserve `admin.hich.com` for a separate privileged RP/origin; it is not mapped to a company or exposed by this foundation. Credentials are enrolled separately per RP; no cross-company credential sharing is assumed. Hostnames containing customer HTML/scripts or delegated DNS must not be allowed ceremony origins. Reassignment, aliasing and hostname changes require reviewed reenrollment/revocation, never automatic RP migration. DNS ownership, TLS and approved production hostnames still require operator verification before MFA exposure.

Use native Spring Security WebAuthn in the next factor stage. Require user verification, exact RP/origin, account/ceremony/session-bound single-use challenges, current policy and credential ownership. UV does not prove hardware binding or which biometric/PIN was used. Privileged policy retains reviewed attestation, trusted metadata and backup/sync assurance; missing evidence denies the role. Support multiple authenticators and protect factor removal. TOTP is only an explicitly approved alternative under existing company/role policy, with encrypted secrets and atomic accepted-step consumption. Recovery never downgrades mandatory assurance. Stage 03 adds native company-bound WebAuthn ceremonies and explicitly permitted TOTP. Password-only sessions remain denied when any policy or enrolled factor requires MFA. Accounts/memberships marked privileged and PLATFORM_ADMIN remain denied pending reviewed hardware attestation/metadata. No partially authenticated session receives company authority.

## Identity and framework integration

Platform identity uses a unique, normalized ASCII email (strip surrounding whitespace, Locale.ROOT lowercase, no provider alias folding), UUID account ID, status, verified-email flag, MFA/privilege policy and security version. Registration hashes before a uniqueness-conflict-safe insert and returns the same 202 result for existing/new valid identities. New accounts are PENDING/unverified with no membership or session. Activation, verification and invitations remain separate reviewed workflows; do not manually activate real users to bypass their absence.

Spring DaoAuthenticationProvider verifies Argon2id passwords and upgrades weaker parameters through a compare-and-set password service. The starting hash profile is 64 MiB, three iterations, one lane, random 16-byte salt and 32-byte output; deployment hardware calibration remains required. Passwords support 15–128 characters, paste and password managers. Registration requires a nonempty operator-reviewed SHA-256 compromised-password corpus; missing corpus denies registration. This is a private local screening file, not a remote password disclosure protocol. Corpus completeness and update procedure are operator release gates.

A thin AuthenticationProvider composes native password verification with a single PostgreSQL INSERT…SELECT that issues a company-bound session grant only for current active, verified, entitled, non-MFA/nonprivileged authority. The stored principal contains only grant/account/company IDs, hostname, version snapshots, creation time and assurance policy. Password hashes never enter Redis sessions. Login uses native UsernamePasswordAuthenticationFilter, ChangeSessionIdAuthenticationStrategy, CsrfAuthenticationStrategy and HttpSessionSecurityContextRepository. Invalid identity/password/status/membership/MFA failures have generic responses. Redis atomic account/source budgets limit login/registration; edge protection and production source attribution still require review. There is no frontend-issued role or token authority.

## Authority, expiration and failure ordering

Ordinary limits are 30 minutes idle and 12 hours absolute; privileged policy retains 15 minutes idle and 8 hours absolute, with five-minute transaction step-up freshness. Hardware-required login remains blocked. OWNER/ADMIN/MANAGER company roles require MFA and use the retained 15-minute idle/8-hour absolute limits; ordinary employee sessions retain 30 minutes/12 hours. Redis enforces inactivity; the request guard checks fixed absolute age and PostgreSQL also checks durable creation time. Exact deadlines reject. Framework activity can refresh idle time, never absolute lifetime; meaningful-interaction-only idle tracking remains an explicit frontend/security follow-up before polling UI integration.

Every restored authenticated request checks the PostgreSQL writer for the grant, account status/verification/version, current active membership/version, company hostname/status/entitlement/version and MFA/privilege flags. No Redis allow cache exists. Automatic PostgreSQL triggers increment versions on policy/status changes, preventing disable/reactivate from restoring old sessions. Membership rows with referenced sessions cannot be deleted and recreated because of foreign keys; revoke/deactivate first and preserve history. Password-change/reset workflows must increment account security_version in the same transaction (parameter-only rehash does not). Required PostgreSQL/Redis failures deny access; no public-schema, local-session or stale-cache fallback is available.

Login commits the PostgreSQL grant before saving the Redis SecurityContext. A Redis failure can leave an unusable orphan ledger row, never authorize from PostgreSQL alone. Logout commits revocation before Spring invalidates the Redis session or acknowledges success. If PostgreSQL revocation fails, logout cannot report success. If Redis deletion fails after commit, the remaining Redis copy is denied by PostgreSQL. Restoring a stale Redis copy cannot bypass committed revocation. Redis missing/expired data requires login; the database never reconstructs a browser session automatically. Redis session data must be protected as authentication authority, with private TLS, restricted ACLs and no public access.

A request checked just before revocation may already be in flight. The foundation exposes no ERP mutation endpoints. Future sensitive mutations must revalidate/lock current authority and consume transaction-bound step-up and independent approval in their business transaction; a request filter alone is not a commit fence. Long-running jobs must reauthorize independently, with bounded work and explicit context lifecycle. Database restoration can restore revoked state: keep ingress closed, fence old writers, invalidate all Redis sessions with a fresh namespace, reconcile durable authority from independent evidence and require fresh authentication before reopening. This operational recovery protocol is required but not automated or verified here.

## Request boundary and future authorization

The Stage 02 csrf/session/register/login/logout contracts remain. Stage 03 adds only the exact POST MFA and account-protection endpoints documented in its handoff under `/api/v1/auth`; all other API paths still deny. Unknown endpoints deny by default. `COMPANY_SESSION` is a coarse authenticated-session marker, not an ERP business role; new endpoints require explicit application authorization, object/field permissions, entitlements and transaction fences. An authenticated request binds/closes the existing TenantContext only after current authority checks; existing connection-routing/reset/cache code remains unchanged and is not a sandbox for compromised shared-process code.

Every state-changing request requires native synchronizer CSRF protection plus the exact current company Origin. Cross-company/sibling CORS is denied, even when both company origins are configured. Duplicate/unknown/noncanonical Host, insecure transport and wrong/null Origin fail. Forwarded headers have no authority; `server.forward-headers-strategy=none`. The production proxy must preserve canonical Host and establish TLS to the application connector, or a separately reviewed trusted-proxy adapter must precede deployment. Do not simply enable trust of arbitrary forwarded headers. No CORS wildcard or shared-domain cookie exception is allowed.

## Stage 03 implementation applicability

The [Stage 03 handoff](../security/phase04-stage03-mfa-account-protection.md) is the current operator and verification reference. A password-verified, company/host/browser-bound transaction lasts at most five minutes and grants no ERP authority. PostgreSQL stores challenge options with two-minute expiry, commits consumption before verification and locks current account/company/membership state for factor mutations. Only a fresh allowed factor followed by native SecurityContext persistence can create a company session; assurance elevation rotates session IDs and full authentication rotates CSRF state.

First-factor setup needs a company-bound, expiring email-ownership or trusted-provisioning approval. It is consumed on the first confirmed enrollment. Native WebAuthn registration requires UV and exact RP/origin but does not itself complete MFA: a separate fresh signed assertion must follow. Existing-factor changes require recent MFA. Removal is enroll-first, prohibits deleting the last usable factor and clears prior verified state until a remaining factor is proved. None attestation is allowed only for ordinary/company MFA, with no hardware claim. Hardware-required roles cannot use this path, TOTP, recovery codes or an enrollment approval to bypass attestation policy.

TOTP uses maintained java-otp, a 30-second step, six ASCII digits, ±one-step tolerance and an atomic increasing PostgreSQL accepted-step fence. Secrets are AES-256-GCM encrypted with account/company/purpose context and an operator keyring. The only intended disclosure is a one-time provisioning response to the approved, CSRF-protected enrollment browser; raw secrets never enter logs, storage, outbox events or ordinary APIs.

Recovery codes are 256-bit random values shown once and stored only as digests. Password plus a current company recovery code atomically invalidates that company's factors, revokes account sessions and permits restricted reenrollment; it cannot itself mint ERP authority. Hardware recovery remains restricted pending independent assurance/approval. Verification, enrollment and password-reset tokens are random, purpose/address/host/version-bound, fifteen-minute and single-use. Password reset preserves MFA/factors and revokes sessions. Notifications and sensitive delivery tokens are queued transactionally; delivery payloads are encrypted and no external email provider is implemented or claimed functional.

## Remaining release gates

Stage 03 has not been compiled or executed by the agent. The owner must resolve the declared TOTP dependency, run all original 280 tests plus new coverage, review V3 privileges and verify the actual browser flow at `/account-security`. Hardware attestation/metadata and independent privileged recovery, real email delivery, RBAC/object/field checks, business operation-bound step-up/dual approval, tenant mutation commit fences, independent audit/retention, infrastructure protection and restore reconciliation remain release gates. A request-time authority filter or generic recent MFA must not be described as a business transaction approval. Valid stolen session cookies remain replayable within current authority/lifetime checks; no browser proof-of-possession equivalence is claimed.

First confirmed enrollment also persists the member’s MFA requirement. Optional MFA opt-in therefore survives factor recovery/deletion, and clearing factors in restricted recovery cannot reopen password-only company access.
